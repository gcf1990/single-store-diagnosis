# 邀约详情客户洞察设计

## 1. 背景与当前事实

单店销售诊断工作台的深度分析包含“电话邀约”和“试驾接待”两个明细域。当前实现中，电话邀约明细详情没有 Tab，仅展示基础信息、命中问题、客户/顾问原文和具体问题摘要；试驾接待明细详情已经是四 Tab 结构，包含“诊断结果 / 试驾质检 / 客户洞察 / 试驾录音”。

历史 PRD 与 DEV-PLAN 明确把试驾质检、客户洞察、试驾录音限定在试驾接待详情中，并明确排除电话邀约详情：电话邀约抽屉不渲染、不请求三个试驾补充模块。本次设计是对该历史范围的新增变更：仅为电话邀约明细详情增加“客户洞察”，不改变试驾详情既有设计。

成熟销售会话智能产品通常把通话洞察聚焦在客户关注点、异议、满意度、竞品提及和原文证据。当前给定数据源也支持这些内容，但不支持试驾截图中的年龄、性别、婚姻状态等客户画像字段。因此本次不复制试驾“客户画像”区，也不新增 AI 总结。

## 2. 目标用户与使用场景

V1 只服务一种用户：单店或小区管理者在电话邀约明细中复盘单通邀约通话。

核心场景：

- 管理者从“电话邀约”明细清单打开某条负向邀约记录。
- 先看“诊断结果”确认该通电话命中的邀约问题和原文证据。
- 切到“客户洞察”查看客户真实关注点、满意度、竞品提及和可追溯引用，辅助复盘顾问下一次如何承接客户。

V1 成功标准：用户能在单通电话详情内看清“客户关注什么、情绪如何、有没有竞品、证据原话是什么”，且所有展示均来自 q31 数据源原始字段，不生成新判断。

## 3. 范围

### 3.1 本次包含

- 仅在 `super-app` 的单店应用“电话邀约”明细详情中新增客户洞察。
- 电话邀约详情改为两个 Tab：“诊断结果 / 客户洞察”。
- “客户洞察”Tab 懒加载 q31 数据源。
- 复刻观远页面 `q5cc2419e84544d089e09075` 中单条详情可用的“关注点概述”和“客户关注点明细”能力。
- 独立展示竞品洞察、客户关注点概述和关注点证据明细。
- 定义正常、加载、空、错误、无权限、无效 ID、快速切换旧请求隔离状态。

### 3.2 本次不包含

- 不改明细清单列结构、筛选、分页、排序或行点击逻辑。
- 不改电话邀约诊断结果、命中问题、原文证据和负向邀约占比口径。
- 不改全局日期、品牌、组织、车系筛选逻辑。
- 不改试驾接待四 Tab、试驾质检、试驾客户洞察、试驾录音和试驾三张补充表请求。
- 不展示 q31 页面中的 TOP100、竞品榜、KPI、满意度说明、客户画像或 AI 总结。
- 不展示手机号，不使用手机号做关联，不新增写回动作。

## 4. 数据源与关联

### 4.1 数据源

| 项 | 内容 |
|---|---|
| 数据集 ID | `q31f6fc089e7540bf9b850a9` |
| 父目录 ID | `kf50c550341894c5399a66b6` |
| 来源页面 ID | `q5cc2419e84544d089e09075` |
| 数据集名称 | `[直连][市场营销数据应用集市]ip电话顾问跟进ai打标结果解析客户关注点表&ads_sale_mart_ipcall_cons_follow_ai_analy_c_cust_concern_point_comb_wms` |
| 粒度 | 一通 IP 电话 + 一个客户关注点 |
| 只读边界 | 仅查询，不写入、不绕权、不扩权 |

### 4.2 精确关联规则

- 电话邀约明细中的 `record.eventId` 是当前通话的 `呼叫编码`。
- 客户洞察查询只使用 `record.eventId` 精确匹配 q31 的 `IP呼叫ID` / `ipcall_id`。
- `record.eventId` 支持纯数字、字母数字和 `sip-...` 等字符串形态。
- 不复用试驾详情的纯数字 `receive_id` 校验。
- 禁止使用客户姓名、顾问、手机号、呼叫时间或其组合做兜底关联。
- `record.eventId` 缺失、空字符串或全空白时，不发起 q31 查询，直接进入 `invalid-id` 状态。
- 按 `IP呼叫ID` 无匹配结果时，进入客户洞察空态，不影响“诊断结果”Tab。

## 6. 页面结构

### 6.1 邀约详情 Tab

电话邀约详情从单正文调整为两个 Tab：

1. 诊断结果
2. 客户洞察

默认打开“诊断结果”。切换到“客户洞察”时才发起 q31 查询。已经成功加载过同一 `eventId` 的数据可在当前抽屉生命周期内复用；重新打开另一条明细时按新 `eventId` 重置状态。

### 6.2 客户洞察 Tab 内顺序

客户洞察 Tab 固定顺序：

1. 竞品洞察
2. 客户关注点概述
3. 关注点证据明细

竞品洞察固定置顶，但仅在任一竞品字段有值时显示。无竞品数据时隐藏整个竞品洞察模块，不展示空壳。

## 7. 竞品洞察

竞品洞察从关注点卡中独立出来，避免在每张关注点证据卡中重复露出竞品字段。

展示规则：

- 只要某行 `competitor`、`compet_desc`、`compet_sum` 任一字段有值，该行参与竞品洞察。
- 按 `competitor + compet_desc + compet_sum` 完整组合去重。
- 完全相同组合只展示一次。
- 不同组合展示为多张竞品卡。
- 每张卡只展示有值字段：竞品、竞品描述、竞品总结。
- 竞品洞察不参与满意度分组，不作为顶部关注点标签。

状态规则：

- 有竞品且有关注点：先展示竞品洞察，再展示关注点概述和证据明细。
- 有竞品但无可展示关注点：展示竞品洞察，并在关注点区域显示“暂无本次通话客户关注点明细”。
- 无竞品但有关注点：隐藏竞品洞察，直接展示客户关注点概述和证据明细。
- 全空：展示客户洞察空态。

## 8. 客户关注点概述

概述模块用于快速扫出客户关注什么和情绪如何。

展示规则：

- 全部关注点均展示，不只展示负向或 TOP 关注点。
- 满意度排序固定为：不满意、满意、中性、其他/未评级。
- 第一层按满意度分组。
- 第二层按关注大类 `label` 分组。
- 每个分组内展示具体关注点 `focus` 标签。
- 点击具体关注点标签后，平滑定位到下方对应证据卡，并把焦点移到目标证据区域。
- 如果 `focus` 为空但 `label` 有值，概述标签使用 `label`。
- 如果 `label` 和 `focus` 均为空，但该行有引用、满意度或竞品信息，该行仍保留在明细中，概述中不生成空标签。

满意度归类规则：

- `satisfaction` 精确或归一后为“不满意”时进入“不满意”。
- 为“满意”时进入“满意”。
- 为“中性”时进入“中性”。
- 其他非空值进入“其他”。
- 空值进入“未评级”。
- “其他”和“未评级”在展示层可合并为“其他/未评级”组，但原始满意度字段在证据卡中仍按原文展示。

## 9. 关注点证据明细

证据明细承载每条客户关注点的完整依据。

分组规则：

- 第一层按满意度排序。
- 第二层按关注大类排序，使用中文 locale 稳定排序。
- 分组内按具体关注点排序；只有完整去重组合一致、仅 `etl_time` 不同时，才保留最新 `etl_time` 对应版本。

去重规则：

- 完全相同关注点重复去重。去重键包含：`label`、`focus`、`satisfaction`、`satis_cate`、`satis_support`、`quote`、`competitor`、`compet_desc`、`compet_sum`。
- 同一关注点但证据不同，必须保留。
- 同一证据但关注点不同，必须保留。
- 同一组合不同 `etl_time` 视为重复版本，只保留最新版本。

证据卡字段顺序：

1. 具体关注点标题：优先 `focus`，为空用 `label`，均为空则使用“未命名关注点”。
2. 满意度：有值才展示。
3. 满意度类别：有值才展示。
4. 满意度依据：有值才展示。
5. 引用原文：有值才展示。

空字段不显示字段标题、空标签、空容器或占位符。

### 9.1 quote 解析

`quote` 处理规则：

- 如果是 JSON 数组字符串，逐项解析。
- 每条引用根据前缀拆为客户/顾问气泡：
  - `客户:`、`客户：`、`顾客:`、`顾客：` 识别为客户气泡。
  - `顾问:`、`顾问：`、`销售:`、`销售：` 识别为顾问气泡。
  - 无可识别前缀时显示为“原文”气泡。
- 解析失败时保留原字符串，显示为“原文”气泡。
- 空数组、空字符串和仅空白不渲染引用区域。

## 10. 状态与异常处理

客户洞察 Tab 独立管理状态，不影响诊断结果 Tab。

| 状态 | 触发条件 | 页面表现 |
|---|---|---|
| `loading` | 用户首次切到客户洞察且请求未完成 | 展示客户洞察加载态 |
| `success` | q31 查询成功且有竞品或关注点内容 | 按固定顺序展示模块 |
| `empty` | q31 查询成功但无匹配行，或匹配行没有可展示字段 | 展示“暂无本次邀约客户洞察” |
| `error` | 网络、接口、SQL 或解析异常 | 展示错误摘要和当前模块重试入口 |
| `forbidden` | HTTP 401/403 或错误信息包含无权限、未授权、forbidden、permission、access denied | 展示无权限提示，不展示重试为主操作 |
| `invalid-id` | `record.eventId` 缺失、空字符串或全空白 | 展示“该邀约记录缺少有效 IP 呼叫ID” |

快速切换隔离：

- 每次打开新明细或切换到新 `eventId` 时生成新的请求 token。
- 请求返回时同时校验 token 和当前 `eventId`。
- 旧请求晚于新请求返回时不得回写当前抽屉。
- 关闭抽屉后返回的数据不得重新打开或污染下一条记录。

## 11. Mock 场景

Mock 数据必须覆盖以下场景：

- 一通电话多行关注点，含不满意、满意、中性、其他/未评级。
- 同一满意度下多个关注大类和多个具体关注点。
- quote 为 JSON 数组，含客户、顾问和无前缀原文。
- quote 解析失败，保留原字符串。
- 竞品字段多行重复组合去重。
- 多个不同竞品组合展示多张卡。
- 无竞品但有关注点。
- 仅竞品但无关注点。
- q31 无匹配数据。
- q31 返回行全为空。
- 请求 error。
- 请求 forbidden。
- 快速切换两条邀约记录，旧请求不得覆盖新记录。

## 12. 测试与验收

### 12.1 单元与服务层验收

- 构造 SQL 时只使用 `record.eventId` 匹配 `IP呼叫ID` / `ipcall_id`。
- 字母数字和 `sip-...` 形态 ID 可正常查询，不被纯数字校验拒绝。
- 空 ID 不发起请求并返回 `invalid-id`。
- 字段映射符合本设计第 5 节。
- 满意度排序固定为“不满意 → 满意 → 中性 → 其他/未评级”。
- 关注点去重保留不同证据，完全相同重复行只保留最新版本。
- 竞品按 `competitor + compet_desc + compet_sum` 去重并独立输出。
- quote JSON 解析、气泡归类和解析失败 fallback 均有覆盖。

### 12.2 组件与交互验收

- 电话邀约详情显示两个 Tab：“诊断结果 / 客户洞察”。
- 默认打开“诊断结果”。
- 首次切到“客户洞察”才请求 q31。
- 点击顶部具体关注点标签能平滑定位到对应证据卡。
- loading、empty、error、forbidden、invalid-id 均可独立验证。
- 有竞品无关注点、无竞品有关注点、全空三类状态表现符合本设计。
- 键盘可切换 Tab，焦点顺序清晰，证据定位后目标可获得焦点。
- 窄侧栏下标签、长原文、长竞品描述不溢出、不遮挡关闭按钮。

### 12.3 回归验收

- 试驾详情仍保持四 Tab：“诊断结果 / 试驾质检 / 客户洞察 / 试驾录音”。
- 打开试驾详情不请求 q31。
- 打开电话邀约详情不请求试驾质检、试驾客户洞察、试驾录音三张表。
- 电话邀约原“诊断结果”内容、命中问题、原文证据、具体问题摘要保持不变。
- 明细清单、标签分布、顾问表现、负向邀约占比、全局筛选、GIO 埋点不因本次变更改变口径。
- 编译与验证通过：`npm run lint`、`npm run build`、`npm run verify:gio`、`npm run verify:vehicle-series`。
